# Magazyn plików zgodny z S3

Skopiuj `.env.example` do `.env` w głównym katalogu i uzupełnij endpoint,
istniejący bucket, region oraz klucze dostępowe. `.env` jest ignorowany przez Git.
Ustaw `EDOCUMENTS_STORAGE=s3`, a następnie uruchom ponownie backend:

```powershell
& ./.runtime/python/python.exe -m pip install -r backend/requirements.txt
& ./.runtime/python/python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Bucket powinien być prywatny. Konto aplikacji potrzebuje uprawnień
`s3:PutObject`, `s3:GetObject` i `s3:DeleteObject` dla prefiksu `edokumenty/*`.
Aplikacja nie tworzy bucketu i nie zmienia jego uprawnień.
Dla serwerów wymagających innego sposobu adresowania ustaw
`S3_ADDRESSING_STYLE=virtual`. Własny certyfikat CA można wskazać przez
`AWS_CA_BUNDLE`; weryfikacja TLS pozostaje włączona.

Nowe pliki są zapisywane w S3 pod losowymi kluczami. W PostgreSQL pozostają
metadane, bucket i klucz obiektu. Pobieranie odbywa się przez backend po
sprawdzeniu sesji lub aktywnego linku udostępnienia. Klucze dostępowe nie
trafiają do przeglądarki. Zmiana bucketu dotyczy nowych plików; wcześniej
zapisane obiekty są odczytywane ze swojego pierwotnego bucketu na tym samym
endpointcie. Endpointu nie należy zmieniać bez przeniesienia obiektów.

Istniejące załączniki w PostgreSQL pozostają dostępne; nie są automatycznie
przenoszone do S3. Ponowne przesłanie załącznika zapisuje go w aktualnym
magazynie. Przy `EDOCUMENTS_STORAGE=database` nowe pliki pozostają w PostgreSQL.
Błąd S3 zwraca błąd operacji — nie przełącza zapisu do bazy.
Nieudane usunięcie starego obiektu jest odnotowane w logu backendu;
może wymagać późniejszego sprzątnięcia obiektu w magazynie.

Konfiguracja klienta: https://docs.aws.amazon.com/boto3/latest/guide/configuration.html
